# GITPulse MVP Roadmap

## Текущее состояние

В проекте уже реализованы базовые части MVP:

- выбор локального Git-репозитория;
- сохранение списка репозиториев;
- загрузка списка репозиториев;
- отображение выбранного репозитория;
- получение `git status`;
- парсинг изменённых файлов;
- выбор файлов для commit;
- создание commit из UI;
- создание snapshot/backup commit;
- запись истории действий;
- отображение истории действий;
- empty-state сообщения;
- обновление status/history после commit и snapshot.

---

## Что нужно сделать сейчас

### 1. Добавить loading-состояния

Нужно защитить основные действия от повторных нажатий.

Добавить состояния:

```ts
const [isLoadingStatus, setIsLoadingStatus] = useState(false);
const [isCommitting, setIsCommitting] = useState(false);
const [isSnapshotting, setIsSnapshotting] = useState(false);
const [isLoadingHistory, setIsLoadingHistory] = useState(false);
```

Применить их к кнопкам:

- `Git status`;
- `Commit`;
- `Snapshot`;
- `Load history`, если такая кнопка есть.

Цель:

- пользователь видит, что действие выполняется;
- нельзя случайно нажать commit/snapshot два раза;
- UI не выглядит зависшим.

---

### 2. Отключать кнопки, когда действие невозможно

Кнопки должны быть disabled, если нет нужных данных.

Примеры:

- нет выбранного репозитория → disabled для `Git status`, `Commit`, `Snapshot`;
- нет выбранных файлов → disabled для `Commit`;
- пустое commit-сообщение → disabled для `Commit`;
- нет изменений → disabled для `Snapshot`, если это уже известно из status;
- действие уже выполняется → disabled для этой кнопки.

---

### 3. Привести backend-аргументы к одному стилю

Во всех Tauri commands лучше использовать одно имя для пути:

```rust
repository_path: String
```

Тогда frontend всегда передаёт:

```ts
repositoryPath: selectedRepo.path
```

Это уменьшает путаницу между:

- `path`;
- `repoPath`;
- `repositoryPath`.

---

### 4. Финально проверить `git.rs`

Проверить, что:

- нет `unwrap()`;
- все команды возвращают `Result<T, String>`;
- ошибки из Git возвращаются через `stderr`;
- `commit message` обрезается через `trim()`;
- snapshot не создаётся, если нет изменений;
- snapshot логируется как `ActionType::Snapshot`, а не `ActionType::Commit`;
- `file_count` в истории корректный.

---

### 5. Сделать базовую ручную проверку MVP

Проверить сценарии вручную:

#### Репозиторий без изменений

Ожидаемо:

- список файлов пустой;
- commit недоступен;
- snapshot недоступен или возвращает понятное сообщение.

#### Репозиторий с изменёнными файлами

Ожидаемо:

- файлы отображаются;
- можно выбрать один или несколько файлов;
- commit создаётся;
- status обновляется;
- history обновляется.

#### Репозиторий с untracked-файлами

Ожидаемо:

- `?? file` отображается нормально;
- файл можно выбрать;
- commit добавляет файл.

#### Пустое commit-сообщение

Ожидаемо:

- commit недоступен;
- backend тоже защищён от пустого сообщения.

#### Двойное нажатие commit/snapshot

Ожидаемо:

- второй запрос не отправляется;
- кнопка временно disabled.

---

## Что сделать следующим этапом

### 1. Добавить просмотр diff для выбранного файла

Минимальный вариант:

- пользователь выбирает файл;
- нажимает `View diff`;
- frontend вызывает Rust command;
- backend выполняет:

```bash
git diff -- <file>
```

Для staged-файлов позже можно добавить:

```bash
git diff --cached -- <file>
```

На первом этапе достаточно показывать diff как обычный текст в `<pre>`.

---

### 2. Улучшить отображение статусов файлов

Сейчас можно оставить простые статусы, но позже стоит сделать понятные подписи:

- `M` → Modified;
- `A` → Added;
- `D` → Deleted;
- `??` → Untracked;
- `R` → Renamed.

Цель — чтобы пользователь не обязан был знать Git porcelain format.

---

### 3. Добавить удаление репозитория из списка

Минимально:

- кнопка `Remove`;
- удалить репозиторий из JSON;
- обновить список;
- если удалён выбранный репозиторий — сбросить `selectedRepo`.

Важно: это не должно удалять папку на диске, только запись из приложения.

---

### 4. Добавить проверку существования сохранённых путей

Если пользователь удалил папку или переместил проект, приложение должно показать это понятно.

Например:

- `Repository not found`;
- `Path no longer exists`;
- `Remove from list`.

---

### 5. Сделать refresh выбранного репозитория при открытии приложения

После запуска приложения:

- загрузить список репозиториев;
- если есть последний выбранный репозиторий — можно выбрать его автоматически;
- загрузить status для выбранного репозитория.

Это не обязательно для первой версии, но улучшает UX.

---

## Что сделать позже

### 1. История по конкретному репозиторию

Сейчас история может быть общей. Позже можно фильтровать:

- вся история;
- история только выбранного репозитория.

---

### 2. Детали history item

Для каждой записи истории можно показывать:

- тип действия;
- путь репозитория;
- дату;
- количество файлов;
- сообщение Git;
- возможно список файлов.

---

### 3. Настройки приложения

Минимальные настройки позже:

- путь хранения JSON;
- включать/выключать auto-refresh;
- дефолтное commit-сообщение для snapshot.

---

### 4. Улучшить snapshot

Возможные улучшения:

- кастомное сообщение snapshot;
- добавлять дату в сообщение;
- показывать список файлов, которые попадут в snapshot;
- не делать snapshot, если изменились только ignored-файлы.

---

### 5. SQLite вместо JSON

Переходить на SQLite стоит только когда JSON станет неудобен.

Причины для SQLite:

- много истории;
- нужны фильтры;
- нужны сортировки;
- нужны быстрые выборки;
- нужно хранить больше метаданных.

Для текущего MVP JSON достаточно.

---

### 6. Улучшить UI

Позже можно добавить:

- нормальные карточки репозиториев;
- цветные статусы файлов;
- панель selected repo;
- toast-уведомления;
- split-view: файлы слева, diff справа;
- фильтр изменённых файлов.

---

## Что пока не делать

Пока не нужно добавлять:

- авторизацию;
- cloud-синхронизацию;
- PostgreSQL;
- Docker;
- отдельный backend-сервер;
- Redux/Zustand;
- сложный Git-клиент;
- merge/rebase;
- branch manager;
- stash manager;
- полноценный diff editor;
- поддержку GitHub/GitLab API;
- сложную систему настроек.

---

## Ближайший коммит

Рекомендуемый следующий коммит:

```text
Add loading states and prevent duplicate Git actions
```

В него должны войти:

- loading-флаги для status/commit/snapshot/history;
- disabled-состояния кнопок;
- защита от повторного нажатия;
- понятный текст на кнопках во время выполнения;
- финальная ручная проверка основных MVP-сценариев.

---

## Следующий коммит после этого

```text
Add basic file diff viewer
```

В него должны войти:

- backend command `git_diff`;
- кнопка `View diff`;
- выбранный файл;
- вывод diff в `<pre>`;
- обработка пустого diff.
